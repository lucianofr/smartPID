## The six questions

### Q1 — Dependency direction
**Verdict:** Both — `project_service.py:11` is *systemic* debt under the "application must not import adapters" rule and a *genuinely new* violation under the stronger "application must not import a driver" rule; and it is the rare violation that costs nothing to remove, because `project_service.py:50`/`:59` already inject the object.

Two distinct rules are in play and the remediation differs, which is why they must not be collapsed:

- **Systemic axis.** `application/workers/db_worker.py:16-17` already imports `adapters.outbound.db_engine` and `adapters.outbound.historian` at module level. The rule "application depends only on ports" is already broken repo-wide. Remediating *that* means introducing outbound Protocols and constructor injection across the worker layer — a program of work, not this PR's job, and correctly out of scope.
- **New axis.** Those are **driven**-side imports: the application reaching for infrastructure it commands. That is the ordinary direction, merely untyped. `project_service.py:11` reaches for an **inbound** adapter — a *driver*, the side that is supposed to call *into* the application. That inverts the drive relationship and closes a package-level loop: `adapters.inbound.api.routers.controllers` → (`app.state`) → `application.project_service` → `adapters.inbound.simulator_adapter`. It does not deadlock today only because `simulator_adapter.py` imports nothing from `application/` — it is one import away from a genuine circular import. Note the contrast with `adapters/inbound/api/dependencies.py:13`, which imports `SimulatorAdapter` under `TYPE_CHECKING` only; `project_service.py:11` is a runtime import.

The decisive point is not the taxonomy: it is that this import purchases nothing. `ProjectService` already receives `simulator_adapter` (`:50`) and stores it (`:59`), and calls it duck-typed at `:259`, `:292` and `:314`. The only reason for the module import is that the helper is a free function. Fix the function form (Q2) and the violation evaporates without a ports program.

### Q2 — Where `bind_opcua_client` belongs
**Verdict:** Make it a method on `SimulatorAdapter` (`simulator_adapter.py:87` → instance method); **acceptable-for-now** as a free function, not a merge blocker.

Rejecting the alternatives:

- **Composition root (`main.py`).** Structurally the most correct home — cross-adapter wiring *is* composition-root work — but unusable: two of the three call sites (`project_service.py:319`, `controllers.py:592`) are runtime, request-scoped, and would have to import `main`, which imports them. `adapters/factory.py:24-33` is the better composition root candidate (it already owns both adapters *and* the simulator-vs-real decision), but the factory is not on `app.state` and is not passed to `ProjectService`; routing it there is a wider refactor than this diff.
- **`application/` behind a port Protocol.** The function's entire payload is `node_id_pv`/`node_id_sp`/`mode_int_map`. Hoisting that into `application/` moves OPC-UA addressing *closer* to the domain, not further. Wrong direction.
- **Leave it.** Works, and every caller is correct — but it forces the `project_service.py:11` import, which is A2.

The method form wins on the ladder: all three call sites already hold a `SimulatorAdapter` instance, so the change is a signature move with zero new imports anywhere, and it removes the only new layering violation in the diff as a side effect. The data it needs (`opcua_node_ids`, `SIMULATOR_MODE_INT_MAP`) is the twin's own. The residual — the twin knowing about the OPC-UA client — is a lateral adapter-to-adapter dependency, but expressed as an injected parameter rather than a module import, which is the form hexagonal architecture tolerates.

### Q3 — The missing port
**Verdict:** No — adding `register_controller` to `TelemetrySource` (`domain/ports/inbound.py:9`) is wrong; it belongs on a narrow Protocol declared in the **adapter** layer, and the shared name across the two flavours is a real smell worth fixing independently.

`TelemetrySource` currently speaks pure domain (`read_telemetry(controller_id) -> TelemetryFrame`). `OpcuaAdapter.register_controller` (`opcua_adapter.py:212-238`) speaks eleven kwargs of OPC-UA node addressing. Widening the domain port to accept them would put protocol strings in the package whose stated contract is zero infrastructure dependency — trading a `# type: ignore` for a contract violation. The `# ---- TelemetrySource ----` section comment above it is simply mis-filed; that is the bug, not the Protocol's omission.

The right shape is a one-method `OpcuaTagBindable(Protocol)` living beside the adapters. It is not a domain concept and must not pretend to be one.

On the name collision: `SimulatorAdapter.register_controller(id, pv_min, pv_max)` (`simulator_adapter.py:323`) and `OPCUAAdapter.register_controller(id, node_id_*, mode_int_map)` (`opcua_adapter.py:212`) are unrelated contracts sharing an identifier, in exactly the two modules `bind_opcua_client` exists to bridge. One Protocol cannot cover both, which is itself the tell. And the codebase already probes the name structurally — `project_service.py:262` does `hasattr(self._simulator_adapter, "register_controller")`, which would happily pass if the wrong adapter were ever injected into that `object | None` slot (`:50`). Rename the outbound flavour to `bind_tags`; that resolves the ambiguity at the source rather than papering it with two same-named Protocols.

### Q4 — `_load_opcua_endpoint` early-return
**Verdict:** Yes, a user can be stranded on the twin; the escape hatch exists but is out-of-band and undiscoverable from the UI; and "simulator presence" is a faithful *proxy* for the right key rather than the key itself — the real problem is not the key, it is that the invariant is enforced in one of four places (A4).

- **Stranding.** With `SPID_SIMULATOR_ENABLED=true`, `project_service.py:326-331` discards the project's persisted `opcua_endpoint` on every open and import. A project commissioned against a real DCS, opened on a daemon that happens to have the simulator on, silently runs against the twin. Every controller reads plausible PV. Nothing in the response, the logs at that point, or `/project/current` says why.
- **Escape hatch.** `PUT /opcua/endpoint` (`opcua.py:75-87`) still writes the meta row and calls `set_endpoint()` with no simulator guard, so an admin *can* force the client onto the real DCS at runtime — but the next project switch calls `_resync_simulator_link` (`:319-320`), which rebinds the client to twin node ids and restarts it without re-asserting the endpoint. So the override survives until the next project operation, then half-reverts into an inconsistent state (real endpoint, twin node ids). The only durable escape is `SPID_SIMULATOR_ENABLED=false` plus a daemon restart — an env var, documented nowhere in the API surface, discoverable only by reading `config.py:74`.
- **The key.** An explicit mode flag already exists: `CoreSettings.simulator_enabled` (`config.py:74`), and it is what `AdapterFactory` itself branches on (`factory.py:24`). Because the factory builds `SimulatorAdapter` if and only if that flag is set, `self._simulator_adapter is not None` is a faithful derivative — not wrong, but an inferred proxy for a declared fact, weakened further by `ProjectService` typing the slot as `object | None` (`:50`) so nothing constrains what may occupy it. Preferring `settings.simulator_enabled` would be marginally more honest; it would not fix anything, because the actual defect is A4's missing enforcement, not the predicate.

### Q5 — Lifecycle / ordering
**Verdict:** The ordering is safe but semantically inverted on two of three paths (A7), the unconditional `sim.start()` can mint a phantom controller on `new_project` (A8), and per-switch rebinding cost is irrelevant at any realistic count — though the extraction did quietly make it O(n²) (A9).

- **Relative to worker startup.** `open_project` (`:138-151`) and `import_project` (`:169-182`) run `_start_control_loops()` — which starts PIDWorker/AIWorker/StatsWorker and adds ids to the IOWorker scan list — *before* `_resync_simulator_link()`. Between them the twin is stopped and the client unbound, so IOWorker skips whole scans. The window is two statements wide (`_load_opcua_endpoint` now early-returns at `:326`, `_start_db_worker` is synchronous), and the new catch-all guards absorb it, so nothing breaks. But it is the wrong order on principle, and it is free to fix. `new_project` is correctly ordered: no controllers exist to bind.
- **Twin OPC-UA server.** Correct by construction: `SimulatorAdapter.stop()` (`:200-206`) deliberately does not touch `_opcua_server`, so the address space and its minted node ids survive the switch. That is why binding after a resync resolves at all.
- **Cost.** Per controller the work is one dict lookup plus one lock-guarded dict assignment (`opcua_adapter.py:239-240`) — no I/O, no network. `list_all()` is one query. **Realistic counts:** the repo declares no maximum anywhere — `config.py` has no `max_controllers`, and the only "4" in the specs (`docs/smartPIDv2.md:290`) bounds the Multi-Trend chart grid, not the loop count. For an edge PID optimizer against a single DCS, tens of loops is the plausible ceiling; at that scale a rebind is microseconds and running it on every switch is the right trade against tracking deltas. The one blemish is A9's accidental O(n²) — still immeasurable at n in the tens, worth fixing only if the file is touched.

### Q6 — L1's NB1 through an architecture lens
**Verdict:** **BLOCKING.** This is a missing lifecycle contract with no owner — the twin has per-entity add/remove but no project-boundary operation, and `ProjectService` has no step that reconciles the twin's controller set against the new project's. Responsibility splits: the *capability* belongs on `SimulatorAdapter` as a new explicit reset, the *decision to invoke it* belongs to `ProjectService`. Not `stop()`.

**Why it is a contract gap, not a stray bug.** `SimulatorAdapter` exposes three lifecycle verbs — `start()` (`:185`), `stop()` (`:200`), `unregister_controller()` (`:345`). The last one proves the adapter *can* drop state; it is called on controller delete. What is absent is any operation meaning "the active project changed." `ProjectService._stop_simulator()` (`:290-295`) calls `stop()` and its docstring at `:300` asserts this drops "the previous project's state" — an assertion the adapter never agreed to. No component owns the invariant *the twin's `_controllers` keys equal the active project's controller ids*, and no component computes the set difference. Before this diff nothing depended on the invariant because telemetry was dead; `_resync_simulator_link` makes the twin authoritative for live PV again, converting an unowned invariant into an observable wrong number.

**Not `SimulatorAdapter.stop()`.** `POST /simulator/stop` (`simulator.py:98-104`) maps straight onto `adapter.stop()` — it is the operator's pause button. Making `stop()` destructive would discard every hand-tuned process model whenever an operator pauses the twin, replacing a state-leak bug with a state-loss bug. `stop()` must stay a thread verb.

**Not `ProjectService` alone.** It cannot reach `_controllers`, and should not; iterating `unregister_controller` per stale id from the application layer would encode the twin's internal bookkeeping in the caller.

**Ruling: split it.** `SimulatorAdapter` gains an explicit `reset_to(ids)` (capability, adapter-owned); `ProjectService._load_simulator_configs()` (`:257`) calls it after `list_all()` and before the registration loop (sequencing, application-owned). That is exactly the boundary hexagonal architecture draws.

**Why BLOCKING and not deferred.** The residual damage is not hypothetical after the upsert half of A1 lands, and it is not rare: controller ids start at 1 in every `.spid`, so *any* two-project workflow reuses ids by default. `load_sim_config` (`simulator_adapter.py:444-450`) partially rescues the case — it overwrites preset/gain/tau/dead_time when the new project happens to have a saved sim-config row for that id, and returns early (`:450`) when the controller is absent. It never touches `pv_min`/`pv_max`. So the leak is: **always** the old project's PV scale, **plus** the whole process model whenever the new project has no persisted sim config for that id — the normal state of a freshly created loop. A wrong PV span means wrong engineering-unit PV into the historian and wrong-scaled PV under alarm evaluation, in the mode this product ships enabled for commissioning and demo. Fix 2 exists specifically to make project switching work with the simulator; shipping it while the twin still models the previous project is shipping the feature with a known wrong-number condition inside its own use case. The remedy is one adapter method plus one call site — the blocker is a missing line of ownership, not a redesign.

---

## Architectural verdict

**The layering as-shipped does not block merge; the unowned twin lifecycle does.** A2/A3 (the `application → adapters.inbound` import and the free-function seam) are a real but zero-cost inversion that should be closed by making `bind_opcua_client` a method — acceptable as-is for this merge. The extraction itself is correct: three genuinely duplicated call sites, one rule, no fourth site missed. A1 is the merge blocker: `_resync_simulator_link` re-arms a twin whose controller state no component owns across the project boundary, and that boundary is the exact scenario the fix exists to enable.
