- bugs-simulator-pid-auto-not-driving-20260730 | Done | "PID em AUTO não está alterando a saída CO mesmo com erro" — reproduced live against the real running daemon, not assumed. Root cause 1 (primary): two independent switches gate the internal PID (`pid_enabled` admin-only via `/pid/enable`, `pid_mode` via `/pid/mode`, operator-reachable) and the tick loop requires BOTH; selecting AUTO alone (`pid_enabled=false`) or enabling alone (`pid_mode=MAN`) each leave CO permanently frozen with zero UI feedback — proved both dead-end combinations directly against `/simulator/status` (error=80, CO stuck at 0 in either case). Fixed by coupling `onSetMode` in `SimulatorControlPanel.tsx`: selecting AUTO now also arms the internal PID for a session that already reaches the config region (`canConfigure` guard — `/pid/enable` is admin-only, so an operator's AUTO click is left unchanged, no new 403). Root cause 2 (adjacent, real): `SimulatorAdapter.enable_pid()`'s `bumpless_transfer(..., current_pv=0.0, ...)` hardcoded the PV baseline instead of the real `ctrl.live_pv`, defeating the whole point of a *bumpless* transfer (manufactures a phantom error_prev/pv_prev on every arm). Fixed to pass `ctrl.live_pv`. Verified with a clean controlled test first (Kp=1/Ti=10/Td=0, SP=80 vs PV≈0 via direct API calls): CO climbed 0 → 84.8 → 88.9 → 92.8 → 96.8 → 100 over 2.5 s once both flags were correctly set, proving the PID math itself was never broken. Backend suite 127/128 green (the 1 failure is the pre-documented `test_opcua_start_stop` port-4849 conflict with the live dev daemon, not a regression). Frontend 15/15, `tsc -b` clean. Re-verified end to end after a full daemon restart: one real UI click on AUTO now fires both `/pid/mode` and `/pid/enable`, and CO climbed 0 → 92 in 1.5 s under load.
