# L3 Security Review — 2026-07-31 frozen diff

Scope: `error_handlers.py`'s global `RequestValidationError` handler / `_json_renderable`,
and the auth posture of the touched routes in `routers/controllers.py`. Non-goals (style,
layering, worker failure modes) not litigated. Line numbers are current working-tree,
not patch offsets. Every non-trivial claim below was settled with a probe, not asserted
— probe scripts lived in `/tmp` outside the repo tree; zero source files were touched.

## Reachability verdict — `_json_renderable` recursion (assignment §1)

**Verdict: reachable, but the crash is in `jsonable_encoder` (FastAPI, pre-existing),
not in this diff's `_json_renderable`; it is bounded to a single authenticated-admin
request returning 500 instead of 422, not a daemon-wide DoS.**

Evidence, in order:

1. **`jsonable_encoder` dies first, `_json_renderable` never runs.** Built a real
   `pydantic.ValidationError` from `ControllerCreate(name=<dict nested N levels>)`,
   extracted `.errors()` exactly as FastAPI does, then called `jsonable_encoder(errors)`
   and `_json_renderable(...)` as two separate, timed steps at N = 200…5000:
   `.errors()` itself never raised (pydantic-core's Rust extraction handles depth
   5000 fine, consistent with the coordinator's parser-depth number). `jsonable_encoder`
   — a **pure-Python, framework function this diff did not write** — raised
   `RecursionError` at **every depth ≥ 995**, before `_json_renderable` (`error_handlers.py:19`)
   ever received a value. At every depth < 995 both succeeded cleanly. So the culprit is
   `jsonable_encoder`, called identically by FastAPI's own stock handler
   (`fastapi/exception_handlers.py:23`, `content={"detail": jsonable_encoder(exc.errors())}`)
   — this vector predates the diff and is not introduced or worsened by it.
2. **End-to-end confirmation through the real ASGI app.** Same nested body, but
   through `httpx.ASGITransport` over the actual `create_app()` (all middleware, real
   `POST /controllers`): clean 422 responses up to depth 950, `RecursionError`
   propagating from depth ≥ 990 on. The ~5-level gap vs. the isolated 995 is exactly
   the extra stack frames the ASGI/Starlette/anyio call chain consumes before your
   code runs — consistent with, not contradicting, finding 1.
3. **A concrete route reaches it.** `POST /controllers` with a wrong-typed `name`
   field (`ControllerCreate.name: str`) whose value is a ~990-level-deep nested dict
   lands the *entire* nested object in `errors()[0]['input']` (confirmed with a real
   request against the real DTO — `dtos/controllers.py:104`). Payload size at the
   crash threshold is ~12 KB — trivial, no size limit would help since this is a
   *depth*, not *size*, attack.
4. **No upstream cap exists.** `adapters/inbound/api/app.py` registers exactly three
   middlewares: `_security_headers` (line 145), `CORSMiddleware` (lines 154-155),
   `TrustedHostMiddleware` (lines 161-162) — none bound body size or JSON nesting depth.
   The only size limit in the app, `settings.max_upload_bytes` (`config.py:64`), is
   wired solely into the multipart `.spid` archive path (`routers/project.py:164`),
   not into any JSON body route.
5. **Blast radius, not "unreachable — don't report a theoretical DoS."** Per the
   auth verdict below, every body-carrying route in `controllers.py` requires
   `require_admin`, so this needs an authenticated admin token. And per Starlette's
   `ServerErrorMiddleware.__call__` (`starlette/middleware/errors.py:186`), the
   framework already sent a generic `500 Internal Server Error` body to the wire
   before re-raising for server-side logging — a real `uvicorn` deployment answers
   with 500 and keeps serving other requests; it does not crash the daemon process.
   (The raw `RecursionError` visible in the probes above is an artifact of
   `httpx.ASGITransport`'s `raise_app_exceptions=True` test semantics, not what a
   live client sees.)

## Auth posture verdict (assignment §2 — the crux)

**One line: the global `RequestValidationError` handler is an AUTHENTICATED
surface for every route this diff touches — FastAPI resolves ALL `Depends()`
(including `require_admin`/`require_user` → `get_current_user`) before it ever
validates the request body, so a request with no credentials gets 401, never 422.**

Evidence:
- `fastapi/dependencies/utils.py:628` — `solve_dependencies()`'s `for sub_dependant in
  dependant.dependencies:` loop (which calls `require_admin`/`require_user` and lets
  `get_current_user`'s `raise HTTPException(401, ...)` — `dependencies.py:110` —
  propagate immediately) runs to completion **before** `request_body_to_args()` is
  even called at line 706 ("body_params checked above"). This is a structural
  guarantee of FastAPI's dependency solver, not incidental ordering.
- Every body-carrying route in `controllers.py` declares `Depends(require_admin)`
  or `Depends(require_user)` alongside its body parameter: `create_controller`
  (line 419), `update_controller` (line 465), `update_alarm_config` (line 689).
  The only routes without a body are the two `require_user` GETs (lines 408, 450, 660).
- Probed directly: unauthenticated request with a malformed (`NaN`) body to
  `POST /commands/setpoint` → `401 {"detail":"Missing or invalid Authorization
  header"}`. Unauthenticated request with a wrong-typed body to
  `PUT /controllers/1` → same 401, before any 422 machinery runs.

## OWASP mapping

- Finding 1 → **A03:2021-Injection** family / **CWE-1284** (the DTO gap lets a
  non-finite value flow past the application boundary unchecked into a live control
  parameter — not classic injection, but the same "unchecked externally-controlled
  quantity" root cause A03 was broadened to cover).
- Finding 2 → framework-level **A04:2021-Insecure Design** (unbounded recursive
  traversal of attacker-shaped input), pre-existing in FastAPI, not this diff.
- No other OWASP category applies cleanly to the handler/route surface reviewed;
  not forcing a mapping onto findings 3-7.
